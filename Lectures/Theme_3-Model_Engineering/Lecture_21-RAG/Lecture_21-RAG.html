This lecture introduces Retrieval-Augmented Generation (RAG), a technique for grounding the responses of Large Language Models (LLMs) in external sources of information. We will first explain the main components of RAG systems, and then implement three RAG pipelines. The first is built step by step using Hugging Face libraries for embedding, retrieval, and generation, the second uses the LlamaIndex framework, and the third uses the LangGraph framework.

21.1 Introduction to Retrieval-Augmented Generation

Retrieval Augmented Generation (RAG) is an approach in which information relevant to a user query is retrieved from external sources and provided to an LLM as context for generating a response. The sources may include websites, local documents, company records, databases, or other documents.

In general, the internal knowledge of LLMs is static, as it is fixed by the date of the used training dataset. Therefore, LLMs cannot reliably answer questions about new events using only the learned knowledge during model training. Updating LLMs with knowledge about current events by continuously retraining the models on new data is an expensive process, as it requires collecting updated datasets and finetuning the model to update the weights. To address this problem, modern LLM-based assistants use web search and other tools to obtain current information. The retrieved information is appended to the context when answering users’ questions and allows to use new facts without retraining the model weights.

RAG involves two major phases:

  • Retrieval, search external sources for information relevant to a user query and select supporting documents and snippets of important information.
  • Content generation, the retrieved supporting information is used as a context that is appended to the user query, and are provided to the LLMs for generating the final response.

Web search followed by an answer based on the retrieved results follows this retrieval-augmented generation pattern.

RAG is also useful for answering questions about private or specialized information that may not be present in a model’s training data. For example, in an enterprise setting, external sources of information for RAG can comprise various company-specific files, documents, reports, policies, and databases. Employing RAG can result in more relevant responses and it can reduce the problem of hallucination by LLMs. When source information is retained and displayed, it also allows the users to review the sources that were used by LLMs and verify the accuracy of generated responses.

Although RAG can improve relevance and reduce unsupported answers, it does not guarantee that the information is current, correct, or sufficient. RAG systems have limitations, such as retrieving irrelevant or outdated information, missing important evidence, and introducing additional processing steps and latency. Retrieved documents can also contain misleading instructions.

21.1.1 Components of a RAG Pipeline

An overview of a RAG system is depicted in the figure.

Figure: RAG system. Source: [1].

Building a RAG system involves the following general steps:

  1. Data loading: the external documents (e.g., text files, PDFs, Word documents, web pages, or databases) are loaded and converted into plain text.
  2. Splitting text into chunks: the text is split into smaller pieces called chunks. Chunking helps retrieval select focused passages and can keep inputs within the context window limits of the models. Chunk size is a tradeoff, where smaller chunks can improve focus, while larger chunks preserve context. Chunks can follow the structure of the document (e.g., one section per chunk), or they can have a fixed size in tokens or characters, often with an overlap between consecutive chunks so that information at a chunk boundary is not lost.
  3. Embedding: each chunk is passed through an embedding model that converts it into a vector embedding. Chunks with similar meaning have embedding vectors that are close to each other.
  4. Retrieval: the user query is converted into a vector embedding with the same embedding model, the query embedding is compared to the chunk embeddings (typically by using cosine similarity), and the top-k most similar chunks are retrieved.
  5. Generation: the retrieved chunks are inserted as context into the prompt together with the user query, and the LLM generates a response using this context.

Steps 1 to 3 prepare (index) the documents before querying. When documents are added, changed, or removed, the index must be updated. Steps 4 and 5 are performed for each query in this basic pipeline. More advanced RAG systems may retrieve information several times while answering a question.

Also, besides such basic RAG pipeline where embeddings are used to find relevant text, there are other types of RAG systems that use keyword search, web search, or hybrid retrieval that combines keyword and embedding-based search.

21.1.2 Vector Databases

The examples covered in this lecture we work with only one document for demonstration purposes, which is split into a small collection of text chunks. For this scale, the embedding vectors can simply be stored as a list or an array in memory. However, in real-world RAG applications with many documents, there are large number of text chunks. E.g., there may be thousands or millions of vector embeddings, and storing and searching is more challenging.

In such cases, vector embeddings are typically stored into a vector store (or vector database). It is a database designed to store and search vector embeddings that represent text, images, audio, or other data. You can think of a vector database in simple terms as an SQL database that instead of data contains high-dimensional vector embeddings. It allows to perform fast similarity search over embeddings, and returns the closest matching vectors for a query. There are many vector databases available, ranging from free open-source to commercial products, offering local and cloud-based solutions.

Also, although a vector database is useful for many RAG applications, it is not a requirement for RAG, as keyword search, web search, and other retrieval methods can also provide context.

21.1.3 Long Context and Web Search

Modern frontier LLMs support context windows of one million tokens or more. When a selected collection of documents fits within the available input context, we can provide the complete text directly instead of retrieving individual chunks. For example, 20 webpages averaging 5,000 tokens each would contain about 100,000 tokens that can all fit into the context window of recent LLMs.

Long context and retrieval solve related but different problems. Retrieval finds relevant information in a larger collection, while long context allows the model to process more of that information at once. An LLM assistant can search the web, select relevant pages, and read their full text when practical. This still follows the broad RAG pattern, even without a second stage of vector-based chunk retrieval, since reading a webpage in context does not permanently add this knowledge to the model’s weights.

For a small set of documents, full-document prompting may be simpler and can avoid losing evidence during chunk retrieval. For a large collection, retrieving selected passages or documents can reduce the amount of irrelevant text and the input-processing cost. Context caching can reduce the cost of reusing a large, stable input. However, a larger context window does not guarantee that the model will correctly find and combine every relevant fact.

The best choice depends on the collection size, question type, answer quality, cost, and latency. Whole-document summaries may benefit from broad context, while a specific factual lookup may need only a few passages. Also, retrieval and long context can be combined to first retrieve relevant documents and then supply their full text.

Split Text into Chunks

To prepare the document for embedding, we will divide the text into smaller chunks so that retrieval can select passages relevant to the query. Chunking can also help keep inputs within input limit of the embedding model and the available context window of the generation model.

As we stated earlier, chunk size involves a tradeoff. Smaller chunks can make retrieval more focused, but may separate a statement from the context needed to interpret it. Larger chunks preserve more context, but may include unrelated information. Smaller chunks do not always produce better embeddings or answers.

Chunks can be based on a token limit, such as 300 tokens, or they can follow the document structure, such as paragraphs and sections. Since this Wikipedia article is already divided into sub-sections, we will use one sub-section per chunk.

The following function chunk_by_section does exactly that, and uses the text markers == to identify top-level headers and split the text into chunks. Its current regular expression needs correction before it can reliably handle nested headings and preserve text before the first heading; see the implementation note near the beginning of the notebook.

# Function to split text into chunks (each sub-section is one chunk)
# The code in this cell is not required in preparation for quizzes
def chunk_by_section(wiki_text):

    # Find all top-level headers and their content
    pattern = re.compile(r'(==\s*[^=].*?==)\s*(.*?)(?=(?:==\s*[^=].*?==)|\Z)', re.S | re.M)
    matches = pattern.findall(wiki_text)

    chunks = []
    pending_headers = []
    for header, content in matches:
        if content.strip():
            # If there are header-only sections, prepend them to non-empty sections
            if pending_headers:
                combined_header = "\n".join(pending_headers + [header])
                chunk = (combined_header + content).strip()
                pending_headers = []
            else:
                chunk = (header + content).strip()
            chunks.append(chunk)
        else:
            pending_headers.append(header)

    return chunks
# Call the function to create chunks
chunks = chunk_by_section(text)

21.2.1 Retrieval with Cosine Similarity

The next step involves finding the most relevant chunks for a given query. We first obtain an embedding vector for the given query using the same model Qwen3-Embedding-0.6B. This results in an 1,024 dimensional embedding vector.

# A test query
query = "What is a mixture of experts"
# Create a vector embedding for the query
query_embedding = embed_model.encode([query], prompt_name="query")[0]
# Print the shape of the embedding
query_embedding.shape
(1024,)

The next cell calculates cosine similarity between the query embedding and the embedding for each chunk. As you may recall, cosine similarity for two vectors \(u\) and \(v\) is calculated as \(\dfrac{u\cdot v}{||u||\cdot ||v||}\).

# Calculate similarity between the query embedding and each chunk embedding
# cosine similarity = dot_product(u,v) / norm(u)*norm(v)
similarities = np.dot(chunk_embeddings, query_embedding)
similarities = similarities / (np.linalg.norm(chunk_embeddings, axis=1) * np.linalg.norm(query_embedding))
# Print the shape of similarities
similarities.shape
(53,)

There are 53 similarity scores since there are 53 text chunks. By sorting the similarity scores, we found that the embeddings for chunks 12, 45, and 15, are the closest to the embedding vector for the query.

# Find the indices for the top 3 most similar chunks

21.2.2 Generation with a Chat Template

The final step in RAG uses the results from the Retrieval phase, and performs response generation. In this section, we use Qwen3-0.6B LLM for response generation. Note that this model is different from Qwen3-Embedding-0.6B that we used for chunk embedding. Also note that the model is loaded with AutoModelForCausalLM since the task to perform is causal language modeling, i.e., predicting the next token from the preceding tokens. Loaded with the model is the corresponding tokenizer as well.

# Load Qwen3 language model and tokenizer

tokenizer = AutoTokenizer.from_pretrained(lm_model_name)

lm_model = AutoModelForCausalLM.from_pretrained(lm_model_name, pad_token_id=tokenizer.eos_token_id)

21.3 RAG with LlamaIndex

This section uses LlamaIndex, which is an advanced framework that facilitates LLMs integration with diverse data sources. LlamaIndex supports knowledge retrieval from over 100 data formats, including PDFs, websites, Word documents, SQL databases, and much more. Besides tools for data retrieval, LlamaIndex offers built-in functions that make RAG implementation quite simple.

Split Text into Chunks

The function SimpleNodeParser in LlamaIndex splits documents into text chunks, referred to here as nodes. Notice that we set the chunks to have approximately 180 tokens, and also there is an overlap of 20 tokens. I.e., the second chunk contains the last 20 tokens from the first chunk. The overlapped tokens help to capture continuity so that the information retrieval is not broken at the chunk boundary. Since this is a short document, there are only 8 chunks, and the first text chunk is shown below.

21.3.1 Vector Store Index and Query Engine

The main difference from the implementation in the previous section is in how the embeddings are stored and searched. Instead of calculating similarity scores with NumPy, we build a VectorStoreIndex over the text chunks, and we search it through a retriever and a query engine. These LlamaIndex components embed the query, perform the similarity search, and return the most relevant chunks, so that the embedding, retrieval, and generation steps below require only a few lines of code.

Embedding

In the next cell we use bge-small-en-v1.5 from Hugging Face as a model for embedding the text chunks.

The cell afterward builds a vector store from the text chunks (nodes). This involves computing an embedding vector for each text chunk using the BGE model, storing all vectors using LlamaIndex’s default in-memory storage, and assigning a retrieval index to the embeddings. This example does not configure a separate persistent vector database. For a larger application, we could connect the index to a supported vector database.

# Load the embedding model
Settings.embed_model = HuggingFaceEmbedding(model_name="BAAI/bge-small-en-v1.5")
# Don't use a default LLM yet, we will define it later
Settings.llm = None
LLM is explicitly disabled. Using MockLLM.
# Index documents using vector store

Retrieval

LlamaIndex offers VectorIndexRetriever which, as it sounds, creates a retriever object that uses the vector index to search for relevant chunks and retrieves the top-1 chunk based on the setting for similarity_top_k in this case. Note that while this keeps the example simple by using the top-1 chunk, some questions may require evidence from multiple chunks. Also, the highest-ranked chunk may still be irrelevant when the document does not contain an answer.

Next, a query engine is defined with RetrieverQueryEngine, that uses the retriever object to return the relevant text for the query.

# Configure retriever
retriever = VectorIndexRetriever(index=index, similarity_top_k=1)
# Create a query engine
query_engine = RetrieverQueryEngine(retriever=retriever)

Generation

For content generation, we will again use Qwen3-0.6B LLM, as in Section 21.2.

The next cell below defines a generation pipeline with the generate_response function. The steps are almost identical to Section 21.2 above, with the exception of the first two lines that call the defined query_engine and extract the text for the most relevant text chunk.

model_name = "Qwen/Qwen3-0.6B"

# Load model

# Load tokenizer
tokenizer = AutoTokenizer.from_pretrained(model_name, use_fast=True)
def generate_response(query):

    # Retrieve the relevant text
    retrieval = query_engine.query(query)

    # Extract the text for the most relevant node
    context = retrieval.source_nodes[0].text

    # Create messages for chat template
    messages = [{"role": "system", "content": "You are a helpful assistant answering questions. Use the provided context to answer questions."},
            {"role": "user", "content": f"""Based on this context: {context}, please answer the following question: {query}"""}]

    # Apply chat template to build the prompt
    prompt = tokenizer.apply_chat_template(messages, tokenize=False, add_generation_prompt=True)

    # Tokenize the prompt
    inputs = tokenizer(prompt, return_tensors="pt").to(model.device)

    # Generate response by the model
    outputs = model.generate(**inputs, max_new_tokens=500, temperature=0.1, top_p=0.95, do_sample=True, pad_token_id=tokenizer.eos_token_id)

    # Decode generated tokens to text
    response = tokenizer.decode(outputs[0], skip_special_tokens=True)

    # Extract the LLM answer only
    answer = response.split("<|im_start|>assistant")[-1].split("</think>")[-1].strip()

    # Print the final answer by the LLM
    print(answer)

21.4 RAG with LangGraph

This section presents a third implementation of a RAG system using LangGraph. LangGraph is a framework developed by the LangChain team for building LLM applications as graphs. The nodes of the graph are Python functions that perform individual steps (e.g., retrieve documents, generate an answer), and the edges define the order in which the steps are executed. The nodes communicate through a shared state, which is a Python dictionary that is passed from one node to the next and updated along the way. The graph-based design makes the structure of an application explicit, and it makes it easy to add steps such as rewriting the query, re-ranking the retrieved chunks, or checking the quality of the generated answer. LangGraph is also one of the most widely used frameworks for building agents, and we will cover it again in the lecture on Agentic AI.

For data loading, text splitting, embedding, and vector storage, LangGraph relies on the components of the LangChain library. Similar to LlamaIndex, LangChain provides document loaders for many file formats, text splitters, wrappers for embedding models and LLMs, and interfaces to many vector stores.

As an external text source in this section, we will use a short plain text file library_guide.txt, which contains a visitor guide for the Maple Hollow Public Library. The library and the town are fictional, and therefore the LLM could not have learned any facts about them during training. Any correct answer to a question about the library must come from the retrieved text, which makes this document a good test case for a RAG system. We will follow the same steps as in the previous sections: data loading, splitting the text into chunks, embedding, retrieval, and generation. The retrieval and generation steps will be implemented as the two nodes of a LangGraph graph.

21.4.1 Defining the Graph with Nodes and Edges

Next, we define the RAG pipeline as a graph with LangGraph. This involves three steps.

1. Define the state. The state is a dictionary that holds the data shared by the nodes of the graph. We define it as a TypedDict with three keys: question is the user query, context is the list of retrieved chunks, and answer is the generated response.

# Define the state of the graph
class State(TypedDict):
    question: str
    context: List[Document]
    answer: str

2. Define the nodes. Each node is a regular Python function that receives the current state, performs one step, and returns a dictionary with the keys of the state that it updates. The retrieve node calls the retriever with the question and stores the retrieved chunks under the context key. The generate node builds the prompt from the context and the question, generates a response with the LLM, and stores it under the answer key. The code in the generate node is the same as in the generate_response function in Section 21.3, except that here the function returns the answer instead of printing it.

# Node 1: retrieve the relevant chunks for the question
def retrieve(state: State):

    retrieved_docs = retriever.invoke(state["question"])

    return {"context": retrieved_docs}
# Node 2: generate an answer based on the retrieved chunks
def generate(state: State):

    # Join the text of the retrieved chunks into a single context string
    context = "\n\n".join(doc.page_content for doc in state["context"])

    # Create messages for chat template
    messages = [{"role": "system", "content": "You are a helpful assistant answering questions. Use the provided context to answer questions."},
            {"role": "user", "content": f"""Based on this context: {context}, please answer the following question: {state['question']}"""}]

    # Apply chat template to build the prompt
    prompt = tokenizer.apply_chat_template(messages, tokenize=False, add_generation_prompt=True)

    # Tokenize the prompt
    inputs = tokenizer(prompt, return_tensors="pt").to(model.device)

    # Generate response by the model
    outputs = model.generate(**inputs, max_new_tokens=500, temperature=0.1, top_p=0.95, do_sample=True, pad_token_id=tokenizer.eos_token_id)

    # Decode generated tokens to text
    response = tokenizer.decode(outputs[0], skip_special_tokens=True)

    # Extract the LLM answer only
    answer = response.split("<|im_start|>assistant")[-1].split("</think>")[-1].strip()

    return {"answer": answer}

3. Define the edges and compile the graph. We create a StateGraph object with the defined state, add the two nodes, and add edges that specify the order of execution: from the special START node to retrieve, from retrieve to generate, and from generate to the special END node. Compiling the graph produces a runnable object.

# Build the graph
graph_builder = StateGraph(State)

# Add the nodes
graph_builder.add_node("retrieve", retrieve)
graph_builder.add_node("generate", generate)

# Add the edges
graph_builder.add_edge(START, "retrieve")
graph_builder.add_edge("retrieve", "generate")
graph_builder.add_edge("generate", END)

# Compile the graph
graph = graph_builder.compile()

The graph in this section has only two nodes connected sequentially, and it performs the same steps as the two previous implementations in the lecture. The benefits of the graph-based design become apparent for more complex RAG pipelines. For instance, we can add a node that rewrites the user query before retrieval, a node that grades the relevance of the retrieved chunks and performs a web search if none of them is relevant, or a node that checks the generated answer for hallucinations and generates a new answer if needed. Such pipelines require conditional edges, where the next node is selected based on the current state, as well as loops, and both are supported by LangGraph.
